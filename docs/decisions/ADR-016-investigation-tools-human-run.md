# ADR-016 — Investigation tools ที่คนกดและที่ AI ใช้: template ต่อ intent, data query guardrails, evidence card, status panel (T-203c/d)

- **Status:** Proposed 2026-11-02 · ผู้ผลิต `backend-dev` · รอ `architect` + `security-reviewer` ตรวจ (N7)
- **Context:** PRD R-5.1–R-5.7, AC-5 · ADR-013 (tool ของ AI, SR106-R8) · ADR-015 §3 (budget ร่วม) · `po` #2 (`EXTERNAL_QUERY` ปิด) · phase-2 breakdown T-203 · mock เท่านั้น (ไม่มี live adapter ก่อน T-208 `[ASK-HUMAN]`)

## Decision

1. **Template เป็นตัว query ไม่ใช่ข้อความ** — `tool_template` (migration 0065) เก็บ filter ของ Logs (`kind=logs`) หรือ SELECT เดียว (`kind=data`) พร้อม `{{name}}` · placeholder ถูกเติมเป็น **string literal ที่ปิดจากข้างในไม่ได้** (logs) หรือ **bind parameter** (`$1..`, data) และค่าต้องเป็นอักขระธรรมดา `[A-Za-z0-9._:@+/-]` เท่านั้น · `org_id` กับ `ticket_id` ระบบเติมจาก ticket และผู้เรียกระบุเองไม่ได้ · placeholder อื่นคนที่กดปุ่มกรอกเอง · บันทึก template ได้เฉพาะ body ที่รันได้จริง (parse filter / `assertReadOnlySql`) · ผูกกับ intent (`intent_id`) หรือ generic (ทุก ticket, **AI ไม่เคยรัน** เพราะ scope ของ AI ต้องมาจาก intent)
2. **คน vs AI ใช้ template เดียวกัน คนละประตู** — คน: `POST /v1/tickets/:id/tools/run` (`investigate.run`) · AI: tool `gcp_logs` / `bigquery_query` ใน `packages/ai` รับแค่ `windowMinutes`/`limit` แล้ว **port ใน worker** หา template ของ scope intent (`run_by_ai`) → ไม่มีข้อความของ ticket หรือของ model เข้า filter/SQL ได้ (planRunbook ไม่ส่ง `query`/`template` อีก) · ทุก guard ของ T-108 ยังอยู่: `resolveToolScope`, allow-list ต่อ intent (`allowed_tools`), role อ่านอย่างเดียว/`AI_TOOLS_WITHOUT_READONLY_LOGIN`, budget ต่อ run/ticket/นาที, `redactToolOutput`
3. **แก้ template = head (`integration.manage`) + audit** — audit เก็บชื่อ, kind, intent และ SHA-256 ของ body (ไม่เก็บตัว body และไม่เคยเก็บ parameter/ผล) `[ASSUMED]` ใช้ `integration.manage` เพราะ template คือ query ไปยังระบบภายนอก; `metric.manage` (T-200) ตั้งใจให้ metric ของ T-205
4. **Ad-hoc = lead/head (`investigate.adhoc`)** — `POST /v1/investigate/adhoc/{logs,data}` ต้องปักผลที่ ticket หรือ incident · filter ต้องอยู่ใน subset ที่ client อ่านได้, ช่วงเวลา ≤ 24 ชม. · SQL ต้องเป็น read เดียว · audit เก็บ HMAC ของ statement/parameter ไม่เก็บตัวข้อความ `[ASSUMED]` (accountability = ใคร/เมื่อไร/hash; ถ้าต้องการอ่านย้อนหลังได้ ให้ผู้ตัดสินเปลี่ยน)
5. **Data query: ความอ่านอย่างเดียวไม่พึ่งการอ่านข้อความ SQL (แก้ตาม security review P1)** — ข้อความ SQL ที่ผ่าน text check ได้ด้วย `--x\r`, `E'\''`, `"'"` หรือ comment ซ้อน และ simple protocol รันหลายคำสั่งได้ (`ROLLBACK; BEGIN READ WRITE; INSERT` จริง) จึงเลิกถือ text check เป็นด่านกั้น: (ก) **ทุก query ใช้ extended protocol** (`queryMode: 'extended'`) ซึ่งเซิร์ฟเวอร์ไม่ยอม parse เกิน 1 คำสั่ง · (ข) statement เป็นตัว **cursor** (`DECLARE … NO SCROLL CURSOR FOR <stmt>` แล้ว `FETCH FORWARD n+1`) จึงรับเฉพาะ SELECT, `--` ท้ายข้อความตัดอะไรที่เราต่อไม่ได้ และ cap แถวทำตอนอ่าน (ไม่สร้างผลทั้งก้อนก่อน) · (ค) `READ ONLY` transaction + `statement_timeout`/`lock_timeout` ต่อ transaction + ค่าเริ่มต้นของ session ตอนเชื่อม · (ง) **role แยกสองชั้น**: login (`NOINHERIT`, ไม่เป็นเจ้าของอะไร, ไม่มีสิทธิ์เอง) → `SET LOCAL ROLE` เป็น `*_reader` ที่มีแค่ column-level SELECT; ไม่มี TEMP/CREATE, ไม่มี EXECUTE ของ `set_config`, `pg_sleep*`, `pg_cancel/terminate_backend` (role แก้ค่าเริ่มต้นของตัวเองได้เสมอ จึงให้ role ที่รัน statement ไม่ใช่ role ที่แก้ได้) · (จ) ชั้นโค้ด (`assertReadOnlySql` ที่อ่านแบบ Postgres: `--` จบที่ `\r`/`\n`, comment ซ้อน, `E'…'`, `"…"`; allow-list ชื่อคอลัมน์ `DATA_COLUMN_ALLOW_LIST` + `allowed_columns` ของ template) เป็นมารยาทและชั้นที่สอง · test: payload 23 แบบยิงตรงเข้า executor บน Postgres จริง แล้วตรวจว่าข้อมูล/role/ตารางไม่เปลี่ยน
5c. **Function: เพิกถอนตามชนิด ไม่ใช่ตามชื่อ (re-review P1/P2)** — denylist ชื่อแพ้ซ้ำ ๆ: `pg_advisory_lock` กิน lock ทั้ง cluster จน `53200`, `pg_logical_emit_message` เขียน WAL 196 MB ใน READ ONLY, `"dblink"` (quoted) ผ่าน text check · `product-mock.grants.sql` จึง `REVOKE EXECUTE … FROM PUBLIC` ให้ (1) **ทุก function VOLATILE ของ `pg_catalog`** ยกเว้น `random`, `random_normal`, `gen_random_uuid`, `clock_timestamp`, `timeofday` (volatile = มี side effect หรือขึ้นกับอย่างอื่นนอกจากอาร์กิวเมนต์: lock, sequence, WAL, notify, setting, sleep, large object, backend control, file read) และ (2) **ทั้งตระกูลไม่ว่า volatility** ในทุก schema: `pg_(try_)advisory*`, `pg_logical*`, `pg_replication*`, `pg_notify`, `pg_read*`/`pg_ls*`/`pg_stat_file`, `pg_current_wal*`/`pg_wal*`, `txid_*`, `lo_*`, `dblink*`, `pg_cancel*`/`pg_terminate*`, `pg_sleep*`, `set_config` · immutable/stable (operator, cast, aggregate, วันที่, string, math, JSON) ยังใช้ได้ เพราะ operator ต้องมี EXECUTE ของ function ข้างหลัง การเพิกถอนทั้งหมดจึงทำไม่ได้ · ชั้นอื่น: `work_mem=16MB`, `temp_file_limit=64MB`, `max_parallel_workers_per_gather=0` ตั้งให้ login (ตั้งด้วย superuser; query แก้ไม่ได้เพราะไม่มี `set_config`) · **cap ไบต์ที่อ่าน**: executor นับไบต์จาก socket — เกิน 1 MB (soft) หยุดอ่านและคืน `truncated`, เกิน 16 MB (hard) ตัดการเชื่อมต่อทันทีแล้วตอบ `WT002` (แถวเดียวใหญ่ได้เท่าที่ server สร้างได้ cap แถวไม่พอ) · `DISCARD ALL` ก่อนคืน connection · ทุกแถวอ่านเป็นชุดละ 25 แถว
5d. **สิ่งที่ product DB จริงต้องมี — ก่อนเปิด ad-hoc (T-208, `[ASK-HUMAN]`)** — role ของ replica จริงอาจให้ผู้ใช้ revoke เหล่านี้ไม่ได้ (managed DB, owner ไม่ใช่ superuser) จึงบังคับ **ตรวจในโค้ด**: `ProductDbExecutor.hardeningProblems()` ถามว่า reader ยังใช้ advisory lock, logical message, `set_config`, `pg_sleep`, sequence, `pg_terminate_backend`, TEMP, CREATE ใน `public` หรือเป็น superuser ได้หรือไม่ · มีข้อใดเหลือ ⇒ `POST /v1/investigate/adhoc/data` ตอบ 503 และใช้ได้เฉพาะ template ที่ head บันทึก (ตรวจใหม่ทุก 1 นาที; ตรวจไม่ได้ = ถือว่าไม่ปลอดภัย) · สิ่งที่ต้องขอจากเจ้าของ DB จริง: (ก) login `NOINHERIT` ที่ไม่ใช่เจ้าของอะไร + group role ที่มีเฉพาะ column-level SELECT และ login เป็นสมาชิก (`SET LOCAL ROLE`) (ข) revoke ตามข้อ 5c ใน database นั้น (ถ้าทำไม่ได้ ใช้ได้แค่ template) (ค) `REVOKE TEMPORARY, CREATE ON DATABASE … FROM PUBLIC` และ `REVOKE CREATE ON SCHEMA public FROM PUBLIC` (ง) `ALTER ROLE <login> SET work_mem/temp_file_limit/statement_timeout/default_transaction_read_only` (บน Cloud SQL บางตัวต้องตั้งเป็น database flag) (จ) ชี้ที่ **read replica** เสมอ ไม่ใช่ primary (ฉ) ถ้าเป็น BigQuery: `maximum_bytes_billed` ใช้กับ federated query ไม่ได้ จึงไม่ใช้ `EXTERNAL_QUERY` · ไม่มี `[CONFIRMED]` ว่า provider ของเจ้าของอนุญาตข้อ (ข)/(ง) — ตรวจกับของจริงที่ T-208
5e. **ยังไม่ปิด: หน่วยความจำฝั่ง server ต่อ statement (ส่งต่อ T-125)** — `SELECT array_agg(repeat('x', 100000000))` หรือ `string_agg` ซ้อนกัน ทำให้ backend กินหน่วยความจำได้หลาย GB; Postgres ไม่มี GUC จำกัดหน่วยความจำต่อ statement (`work_mem` ไม่คุม aggregate/ค่า datum) และเพิกถอน `repeat`/`lpad`/`array_fill` ไม่พอ (ยังมี `||`, `concat`, `string_agg`, `generate_series` ซ้อน) · ที่ทำแล้วลดความเสียหาย: `statement_timeout` 15 วิ, `temp_file_limit`, cap ไบต์ฝั่งอ่าน, ad-hoc เฉพาะ lead/head, ปิด ad-hoc เมื่อ hardening ไม่ครบ · **ที่ต้องทำที่ T-125 (infra):** จำกัดหน่วยความจำของ instance ที่ตอบ product query (container/cgroup limit บน replica ที่ใช้กับ Watchtower โดยเฉพาะ, ไม่ใช่ primary) ให้ OOM-kill ฆ่าแค่ replica นั้น `[UNVERIFIED]` ว่าแนวทางนี้ทำได้บน replica ที่เจ้าของใช้จริง
5a. **Budget เพิ่มพื้นของ AI และเพดานต่อคน (security review P2)** — คน+system รวมกันใช้ได้ไม่เกิน `total − aiFloor` (55 − 10 = 45) เพื่อให้ AI เหลืออย่างน้อย 10 · หนึ่งคนไม่เกิน 20/นาที (หน้าต่างของตัวเองใต้ lock เดียวกัน `person_<resource>:<user id>`) · ทั้งหมด `[ASSUMED]`
5b. **Template ที่ AI รันต้องใช้ `{{org_id}}` (P3)** — ตรวจตอนบันทึก (400), เป็น CHECK ในตาราง (`tool_template_ai_org_check`), `templateForAi` กรองซ้ำ และ port ใน worker ตรวจอีกครั้ง · template ที่ไม่ใช้ `org_id` ตั้ง `runByAi: false` ได้ (ให้คนกด)
6. **DB ของ product แยกจาก DB ของ Watchtower** — `product_mock` ใน Postgres เดียวกัน (compose: one-shot `product-mock-init`; test: `createProductMockDatabase` ใช้ไฟล์ SQL ชุดเดียวกัน) · เชื่อมด้วย `PRODUCT_DB_URL` (ว่าง = ไม่มี DB; นอก local ต้องมี password จริง ≥ 16 ตัว — config ปฏิเสธ) · compose `product-mock-init` อยู่หลัง profile `product-mock` และไม่มี password เริ่มต้น · database ชื่อ `product_mock`/`wt_pm_*` ถือเป็น `sandbox` → ผลติดป้าย mock (N5)
7. **Evidence card (R-5.6)** — `evidence_card` ปักที่ ticket **หรือ** incident (CHECK exactly one) เก็บ: ชื่อ template, สรุป (นับ/ช่วงเวลา, ไม่มีเนื้อหา), **excerpt ที่ผ่าน redactor แล้ว** (N4 — ใช้รายชื่อ contact ของ org เป็น dictionary), HMAC ของ parameter และของผลเต็ม, `mock` · ไม่เก็บผลเต็ม (scope cut) · ลบ (unpin) ได้ มี audit
8. **Status panel (R-5.7)** — `GET /v1/ops/services` (`dashboard.ops.read`): ต่อ service ใน catalog: สถานะ alert, sparkline error rate + p95 24 ชม. (30 นาที/จุด) จาก `MetricsClient`, deploy ล่าสุด, incident ที่เปิด · metrics 1 call/service ผ่าน budget ร่วมและลง `tool_execution` (`agent=status_panel`) · cache 60 วินาที `[ASSUMED]` · budget หมด = `rate_limited`, ไม่มี client = `not_connected` (ไม่เดา)
9. **ข้อตกลงที่ผู้ตรวจควรดู** — (ก) `org_id` ของ template = `organization.id` ของ Watchtower `[ASSUMED]`: product ต้องติดป้าย org ด้วย id นี้ (หรือ T-205 เพิ่มตารางแมป) · (ข) `repo_changes` ของ AI ใช้ intent key เป็น service slug (แปลง `_` เป็น `-`) จนกว่า ticket จะรู้ service ของตัวเอง `[ASSUMED]` · (ค) 1 การเรียก tool ของ AI = 1 หน่วยโควตา จึงอ่านหน้าเดียว (ดู ADR-015 §3)

## Consequences / ยังไม่ยืนยัน

- logs/metrics/repo เป็น fake (`examples/tools/fixtures.json`) ทั้งหมด; ภาษา filter ที่ fake อ่านเป็น subset ของ Cloud Logging (`service`, `labels.k`, `severity>=`, ข้อความ) — **live adapter ต้องผ่าน contract test เดียวกัน (`clients.contract.ts`) และตรวจ syntax กับเอกสารจริงก่อน** `[VERIFY]`
- product DB จริง (BigQuery หรือ Postgres replica), GitHub, Cloud Logging/Monitoring = T-208 `[ASK-HUMAN]`
- allow-list คอลัมน์ (`DATA_COLUMN_ALLOW_LIST`) เป็นรายการทั่วไป `[ASSUMED]` — เจ้าของต้องรีวิวกับ schema จริง และแนะนำให้ใช้ column grant แบบ `product-mock.grants.sql`
- redaction ยังไม่มี NER: ชื่อที่ไม่อยู่ใน dictionary ของ org จะหลุดไปใน excerpt ได้ (ช่องว่างเดิมของ ADR-013)
- ทบทวนเมื่อ: เปิด live adapter, เพิ่ม tool ที่เขียนได้ (ต้องผ่าน gate, N2), ย้ายไป BigQuery (`maximum_bytes_billed` ใช้กับ federated query ไม่ได้)
