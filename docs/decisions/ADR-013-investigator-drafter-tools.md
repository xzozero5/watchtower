# ADR-013 — Investigator, drafter และ tools แบบ read-only (T-108 a–e)

- **Status:** Proposed 2026-11-01 · ผู้ผลิต `ai-engineer` · รอ `architect` + `security-reviewer` ตรวจ (N7)
- **Context:** PRD §6.2/§6.4/§6.5, R-5.1–5.3, AC-4 · ADR-008 §6 (registry ยังไม่มี budget นอก handle) · SR106-R8 (tool scope มาจาก intent ที่ classifier พูดเอง) · ADR-011 (gate) · `po` #26 (LINE verified), #27 (KB publish แยกหน้าที่)

## Decision

1. **Tools (`packages/ai/src/toolkit/`)** — `kb_search`, `similar_tickets`, `org_context` (จริง) และ `gcp_logs`, `bigquery_query`, `repo_changes` (stub อ่านจาก `examples/tools/fixtures.json`, output มี `mock: true` และ card แสดง "(mock data)"). Zod input/output ทุกตัว, input เป็น `strictObject`: **model เลือก ticket/org ไม่ได้** (`similar_tickets` และ `org_context` ใช้ ticket id จาก run) และ BigQuery รับ**ชื่อ template**ไม่รับ SQL
2. **Runbook ต่อ intent = รายการ tool call ที่โค้ดสร้างจาก ticket** (`planRunbook`) — ลำดับ generic ก่อน แล้ว tool ภายนอกตาม `intent.allowed_tools` · **model ไม่เลือก tool call และไม่มี tool loop** (ตัด prompt injection ที่พยายามสั่ง tool) · ผล tool ทุกชิ้นผ่าน `session.redactToolOutput` ก่อนถึง model (N4) · evidence card ที่คนเห็นคือข้อความ redacted แล้ว restore แบบ `customer` (ข้อมูลของ ticket นี้กลับมา, ของคนอื่นคงเป็น placeholder)
3. **SR106-R8** — tool ภายนอก (logs/data/repo) ใช้ได้เมื่อ intent ของ scope มาจาก (ก) คนสร้าง ticket พร้อม intent หรือแก้ intent (`ticket_event` actor `user`) หรือ (ข) brief classify ได้ confidence ≥ `AI_INTENT_SCOPE_MIN_CONFIDENCE` (0.75 `[ASSUMED]`) · นอกนั้น intent = `null` → generic tools เท่านั้น · รายงานบอก `scope.basis`
4. **Budget นอก handle** — ทุก call (รวมที่ถูกปฏิเสธ) เป็นแถว `tool_execution`; นับ per run / per ticket-ชั่วโมง / per tool-นาที จากแถว ใต้ advisory lock ต่อ ticket · ค่า `AI_TOOL_BUDGETS` 12 / 40 / 30 `[ASSUMED]` (Logging API 60/นาที/โปรเจกต์ แบ่งครึ่งให้คน) · เก็บ HMAC ของ input (key เดียวกับ `ai_run`) ไม่เก็บ input/ผล
5. **N2 ที่ชั้น DB** — role `watchtower_ai_ro` (migration 0034) SELECT ได้เฉพาะ view `ai_v_ticket`, `ai_v_ticket_message` (public เท่านั้น, ตัด 1,500 ตัวอักษร), `ai_v_org` (ระบุคอลัมน์ทีละตัว) · worker ใช้ DSN `AI_READONLY_DATABASE_URL`; ว่าง = อ่าน view เดียวกันผ่าน connection ของ worker (**โค้ดล้วน ๆ ไม่ใช่ DB-enforced** `[ASSUMED]` สำหรับ dev) · `kb_search` ใช้ `searchKb` ของ T-107 บน connection ของแอป (ต้องใช้ pgvector และตาราง chunk ที่ view ไม่เปิด) `[ASSUMED]`
6. **Drafter** — ตอบเป็นประโยค `{text, kind, evidenceIds}`: `fact`/`instruction` ไม่มี evidence = uncited (นับ) · id ที่ model แต่งขึ้นถูกทิ้ง · **disclosure ทำด้วยโค้ด** ไม่ใช่แค่ prompt: contact ไม่ verified → ตัดประโยคที่อิง evidence ที่ไม่ใช่ KB `customer` visibility หรือมีลิงก์ แล้วบอกจำนวนที่ตัด · verified = `contact.verified_at`, แต่ ticket ช่อง LINE ใช้ `line_verified_at` เท่านั้น (po #26) · ภาษาตามข้อความลูกค้า (`detectLanguage`), ภาษาต่างกัน/มี placeholder ของคนอื่น = `needs_review`
7. **Autonomy** — stage 0 ไม่ draft · stage 1 draft เมื่อคนขอ (`POST /v1/tickets/:id/ai/requests`) · stage 2 draft อัตโนมัติหลัง investigate · stage ของ ticket's own intent (ที่ gate อ่าน) · ไม่มี path ส่งถึงลูกค้า: draft รอคน, **approve = reply เดิมที่มี `aiDraftId`** (T-122d: ผูก hash + ผู้อนุมัติ) · **edit = reply ที่มี `editedFromDraftId`** (ส่งเป็น origin `human`, เก็บ edit distance แบบ word-level normalised) · reject = 9 รหัส (`other` ต้องมี comment) · ทุกผลลัพธ์อยู่ใน `ai_draft.disposition`
8. **KB author (AC-4)** — resolve → outbox `kb_author` หน่วง 30 วินาที (ถูก reopen = ข้าม) · "ไม่มี citation" = ไม่มี draft ที่คนอนุมัติ/แก้ที่ cite `kind: kb` และยังไม่มีบทความอ้าง ticket นี้เป็น source และมีคำตอบ public จาก staff · สร้างโดย actor `ai` แทนผู้ resolve (`onBehalfOf`): version `authored_by_machine` + `requested_by` · **ผู้สั่ง AI อนุมัติไม่ได้** (`kb_publisher_requested_ai_text`) แม้คนอื่นแก้ต่อแล้ว, break-glass ไม่ได้, AI publish เองไม่ได้ · บทความเป็น `internal` + `in_review` จนกว่าคนที่สองจะ publish และ**ไม่เคย restore placeholder** (placeholder ในผล = ล้มเหลว)

## Consequences / ยังไม่ยืนยัน

- Mock provider เท่านั้น: ข้อความ report/draft/article มาจาก `DevMockLlmProvider` — คุณภาพจริง, ขนาด prompt, p95 < 120 s กับ provider จริง `[UNVERIFIED]` (deadline ของ job 110 s กัน abort)
- ค่า 0.75, 12/40/30, 30 วินาที, word-level distance, ชื่อ template/service = intent key (จนกว่ามี service catalog) เป็น `[ASSUMED]`
- `href` ของ KB (`/kb/<slug>`) ยังไม่มีหน้าใน web (T-107e) · stub ไม่เคยคุยกับ GCP/BigQuery/GitHub จริง
- redaction dictionary ว่างยังเป็นช่องว่างเดิม (ชื่อที่ไม่อยู่ใน dictionary ไม่ถูกจับ); ชื่อ contact ของ org ถูกส่งเป็น dictionary
- ผู้ตรวจควรดู: `resolveToolScope` (เงื่อนไข human-confirmed อ่านจาก `ticket_event`), view allow-list, การ restore `customer` ของ evidence, และกฎ KB publish
- ทบทวนเมื่อ: เปิด provider จริง, เพิ่ม tool ที่เขียนได้ (ต้องผ่าน gate), เปิด stage 3
