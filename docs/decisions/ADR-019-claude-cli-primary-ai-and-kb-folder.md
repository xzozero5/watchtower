# ADR-019 — `claude -p` เป็น AI หลักของ instance เจ้าของ (bridge ใน Docker, ทำงานเมื่อ host online, KB folder นอก repo)

- **Status:** Accepted (แก้ ADR-017 เฉพาะ "dev/POC เท่านั้น" → "AI หลักของ instance ส่วนตัวของเจ้าของ" · ข้อห้าม production/loopback ยังอยู่)
- **Date:** 2026-11-03 (เวลากรุงเทพ) · **ผู้ตัดสิน:** เจ้าของโปรเจกต์ ("AI จะใช้ท่า `claude -p` เป็นท่าหลักไปก่อน … ใช้ sonnet … Watchtower จะใช้ feature AI ต่อเมื่อเครื่อง host online อยู่บน internet … อาจจะทำเป็น docker เปิดค้างไว้ … folder ใน /works เพื่อจัดการ knowledge base")
- **Context:** ADR-017 ทำให้ `claude-cli` ใช้ได้ แต่ต้องเปิด bridge ใน terminal เองทุกครั้ง และ AI ล้มแบบไม่แยกว่า "ไม่มี internet" กับ "พัง" เจ้าของต้องการให้ท่านี้เป็นท่าหลักชั่วคราว ใช้ model `sonnet` ทุก tier รัน bridge ค้างใน Docker และมี folder KB ของตัวเองนอก repo

## Decision
1. **`claude-cli` เป็น provider หลักของ instance เจ้าของ** (ยังเป็นค่าที่เจ้าของตั้งใน env file นอก repo; ค่าที่มากับ repo ยัง `AI_PROVIDER=mock` เพื่อให้ clone ใหม่ไม่ส่งอะไรออก — N1, repo เป็นกลาง) · ทุก tier ใช้ alias `sonnet`: `AI_MODEL_DEEP/STANDARD/LIGHT=sonnet`, `AI_MODEL_PRICES={"sonnet":{"inputUsdPerMTok":0,"outputUsdPerMTok":0}}` ตั้งใน env file และเขียนไว้ใน `.env.example`/runbook เป็นตัวอย่าง (comment) · **ไม่มีชื่อ model ในโค้ด** · `config/models.yaml` ยังเป็นของ AI ที่ "สร้าง" โปรเจกต์ ไม่เกี่ยว
2. **ข้อจำกัด ADR-017 คงไว้ทั้งหมด:** config ปฏิเสธ boot เมื่อ `NODE_ENV=production` หรือ `APP_URL` ไม่ใช่ loopback · พิจารณาผ่อนแล้ว ไม่ผ่อน: เหตุผลที่ตั้งไว้คือกัน instance ที่คนอื่นเข้าถึงได้ส่งข้อความลูกค้าผ่าน subscription ส่วนตัวคนเดียว เหตุผลนี้ไม่เปลี่ยนเพราะเปลี่ยนเป็น "ท่าหลัก" และการผ่อนทำให้ (ก) ข้อมูลลูกค้า (redact แล้ว) ไหลผ่านบัญชีส่วนบุคคลของคนคนเดียวโดยไม่มี DPA ขององค์กร (ข) ความเสี่ยงด้านเงื่อนไขบริการด้านล่างขยายตามปริมาณงาน (ค) ไม่มี SLA เมื่อเครื่อง host ปิด · ถ้าอนาคตจะเปิดให้ทีมใช้จริง ให้ย้ายไป `anthropic`/`vertex` (ADR-008) ไม่ใช่ผ่อนข้อจำกัดนี้ `[ASK-HUMAN]` ถ้าเจ้าของอยากผ่อน ต้องเขียน ADR ใหม่พร้อมคำตอบเรื่องเงื่อนไขบริการ
3. **Bridge เป็น compose service `claude-bridge`** (profile `ai`, `restart: unless-stopped`, read-only rootfs, `cap_drop ALL`, ไม่ publish port ออก host): image `tools/claude-cli-bridge/Dockerfile` ติดตั้ง `@anthropic-ai/claude-code` pin เวอร์ชัน (ARG `CLAUDE_CODE_VERSION`, ค่าเริ่ม `2.1.316` ที่ตรงกับ CLI ที่ทดสอบใน ADR-017; มีอยู่บน npm `[TESTED]` ผ่าน `npm view`) แล้วรัน `server.mjs` ที่ `0.0.0.0:4317` **ภายใน compose network เท่านั้น** · bearer token ยังบังคับ (`CLAUDE_CLI_BRIDGE_TOKEN`) · worker เรียก `http://claude-bridge:4317` · adapter เพิ่ม `claude-bridge` ใน allow-list ของ host (ยังเป็น allow-list เข้ม: เท่านี้ {localhost, 127.0.0.1, [::1], host.docker.internal, claude-bridge}, `http` เท่านั้น, ห้ามมี credential ใน URL) · path เดิม (รัน bridge บน host ด้วย `pnpm claude-bridge`) ยังใช้ได้
4. **Auth ของ container:** `CLAUDE_CODE_OAUTH_TOKEN` จาก `claude setup-token` (token อายุยาว ต้องมี Claude subscription — `claude setup-token --help` ยืนยันว่าคำสั่งมีอยู่ `[TESTED]`; **ชื่อ env var ต้องตรวจกับเอกสาร Claude Code ปัจจุบัน `[VERIFY]`** เพราะ agent นี้เปิดเอกสารออนไลน์ไม่ได้) ส่งผ่าน environment จากไฟล์ env นอก repo ตอน `up` ไม่ฝังใน image ไม่ส่งให้ api/worker · `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` ไม่ถูกส่งเข้า container และ bridge ตัดทิ้งจาก env ของ child อยู่แล้ว
5. **AI ทำงานเมื่อ host online เท่านั้น:** bridge มี `GET /healthz` (ไม่ต้อง auth, ตอบแค่ `{status, online, checkedAt}`) และเช็ค online ด้วย TCP connect ไป `api.anthropic.com:443` (timeout 3 s, cache 15 s, แชร์ probe ที่กำลังรัน) · `POST /v1/generate` ตอน offline ตอบ `503 {"error":"offline"}` **ก่อน** spawn CLI (หลังตรวจ token) · adapter คงเป็น `ProviderError(code=offline, retryable)` → agents แปลงเป็นเหตุผลใหม่ `provider_offline` (แยกจาก `provider_error`/`provider_unavailable`) → `ai_run` ลง error ตามเดิม (audited, **ไม่ fallback เป็น mock** — ADR-008) → งาน brief เขียน insight `needs_human/provider_offline` แล้วถูกเลื่อนไปอีก 5 นาทีด้วย `moveToDelayed` + `DelayedError` (ไม่เผา attempt) จนครบ 24 ชม. นับจากสร้าง job แล้วหยุดให้คนทำเอง · web แสดงเหตุผลด้วยข้อความ "AI ออฟไลน์ … ระบบจะลองใหม่เอง" ในจุดที่แสดงเหตุผลของ AI อยู่แล้ว
6. **KB folder นอก repo:** `WATCHTOWER_KB_DIR` (เครื่องเจ้าของ: `D:\Works\watchtower-kb`) เก็บ Markdown + front-matter (`title, slug?, lang, kind, visibility, tags, intent, orgs`) · `pnpm kb:sync` (`packages/db/src/kb-sync`) นำเข้า `kb_article` + `kb_article_version` แบบ idempotent ด้วย hash ของ title+body และใช้เส้นทางเดียวกับ seed (outbox → `embed_article`) · **กฎความปลอดภัย:** บทความ `internal` เข้าเป็น published; `customer`/`orgs` เข้าเป็น **draft** ให้คนกด publish ในแอป (ไฟล์ sync ไม่ควรทำให้ข้อความถึงลูกค้าโดยไม่ผ่านคน — N3) · ห้าม sync ขยาย visibility ของบทความที่มีอยู่ · version ใหม่ของบทความที่ไม่ใช่ internal รอคน publish · ลบไฟล์ไม่ทำอะไร · โฟลเดอร์ mount อ่านอย่างเดียวที่ `/kb` ใน `claude-bridge` สำหรับใช้ grounding ในอนาคต (ตอนนี้ยังไม่มีอะไรอ่าน)

## Options considered
- **A — bridge ใน Docker + token ยาว (เลือก)** — เปิดค้างได้ ไม่ต้องใช้ terminal; ต้องเก็บ OAuth token ใน env file (นอก repo, N1)
- **B — คงรัน bridge บน host** — ไม่มี token ใน container; ต้องเปิดเอง (ยังรองรับเป็นทางเลือก)
- **C — ผ่อนข้อจำกัด loopback/production** — ไม่เลือก (เหตุผลในข้อ 2)
- **D — ให้ web โชว์ banner AI offline ทั้งระบบ** — ต้องมี endpoint สถานะ AI ที่ api (api ไม่รู้จัก bridge) ยังไม่ทำ; ตอนนี้โชว์ที่ระดับ ticket (ข้อ 5)

## Consequences
- **[ASK-HUMAN] เงื่อนไขบริการของ Anthropic:** การใช้ subscription (Pro/Max) ผ่าน `claude -p` / `setup-token` แบบอัตโนมัติและต่อเนื่อง (รวมข้อความที่มาจากลูกค้า) อาจอยู่นอกการใช้งานที่เงื่อนไข/นโยบายอนุญาต agent ไม่ได้ตรวจเงื่อนไขปัจจุบัน เจ้าของต้องอ่านเอง; ถ้าไม่อนุญาตต้องย้ายไป API key (`anthropic`) หรือ Vertex — ไม่ต้องแก้โค้ด แค่เปลี่ยน `AI_PROVIDER`
- ข้อมูลที่ redact แล้วออกไปที่ Anthropic ผ่านบัญชีส่วนตัวของเจ้าของ `[ASK-HUMAN]` PDPA/ISO ของบริษัทยอมรับหรือไม่ก่อนใช้กับข้อมูลลูกค้าจริง
- ไม่ยืนยันด้วยการรันจริง `[UNVERIFIED]`: image build และ container ที่ login ด้วย `CLAUDE_CODE_OAUTH_TOKEN` (ไม่ได้ build/รัน), ชื่อ env var, ว่า CLI ใน container ต้องการ `~/.claude.json` writable (ตั้ง tmpfs ไว้แล้ว), พฤติกรรม `claude` เมื่อ token หมดอายุ (จะได้ `cli_failed` 502 → `provider_error`), `api.anthropic.com:443` TCP reachable ≠ API ใช้ได้ (proxy/firewall ที่เปิด 443 แต่บล็อก API จะผ่านด่านนี้แล้วไปล้มที่ `cli_failed`)
- ยังไม่ทำ: banner "AI offline" ระดับทั้งระบบ, offline handling ของ investigation/draft job (ยังเข้า retry 3 ครั้งเดิมแล้วแสดงข้อความ offline), การเลื่อน attempt ของ job อื่นที่เรียก AI
- ตรวจซ้ำ: เมื่อ Claude Code เปลี่ยน auth/flag, เมื่อเจ้าของตอบเรื่องเงื่อนไขบริการ, เมื่อจะให้คนอื่นเข้า instance
