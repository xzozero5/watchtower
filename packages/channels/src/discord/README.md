# Discord webhook notifications (T-104a)

One-way notifications to Discord: a transport interface with an in-memory fake and a live HTTP
transport, a webhook-URL value object, message builders and a per-webhook rate-limit tracker. No bot,
no interactions endpoint, no `/ack` (T-202). The fan-out (which event goes to which channel) and the
delivery ledger live in `apps/worker/src/discord`.

| File                    | What it is                                                                                                                                                                  |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webhook.ts`            | `DiscordWebhook`: parses `https://discord.com/api/webhooks/<id>/<token>` only (SSRF guard), redacts the token in `String`, JSON and `util.inspect`                          |
| `message.ts`            | message schema with Discord's limits, `buildPayload` (adds `allowed_mentions: { parse: [] }`), `buildTicketCreatedMessage` (key, priority, channel, link; no customer data) |
| `transport.ts`          | `DiscordTransport` (`kind`, `execute`) and `DiscordSendResult.delivered`                                                                                                    |
| `fake.ts`               | `FakeDiscordTransport`: records in memory, `delivered: false` always, `revoke`, `limitRate`, `failNext`                                                                     |
| `live.ts`               | `LiveDiscordTransport`: injected `fetch`, `redirect: 'manual'`, `Retry-After` and bucket headers, dead-webhook breaker, no retry after an unknown outcome                   |
| `rate-limit.ts`         | `DiscordRateLimiter`: per-webhook bucket from `X-RateLimit-*`, global 429                                                                                                   |
| `adapter.ts`            | `DiscordAdapter` (`send`; `ingest` and `markRead` unsupported; `capabilities`)                                                                                              |
| `transport.contract.ts` | one contract for fake and live; live only with `CONTRACT_LIVE=1` (`[ASK-HUMAN]`), posting also needs `CONTRACT_LIVE_WRITE=1` and `DISCORD_CONTRACT_WEBHOOK_URL`             |

Mock versus live is decided by the caller, never here, and a fake can never say `delivered: true`.

## The bot: buttons, threads, interactions (T-202b)

`bot.ts` (`BotTransport`, message schema, wire payload), `bot-fake.ts` (`FakeBotTransport`, the only
implementation in Phase 2: no token, no network, `delivered` always false, never returns an id),
`bot-messages.ts` (the pages and lines Watchtower posts, built from ids, enumerations, counts and
catalog names only; N4), `interactions.ts` (Ed25519 verification, payload and response shapes). A live
bot transport is a later task behind `[ASK-HUMAN]` (bot token, channel, application, public key).
